TL;DR

Human or LLM? Look at the comments.

The task: given a code snippet, say whether a human or an LLM wrote it. The catch is that training data covers three languages and one domain, while the test set adds five unseen languages and two unseen domains.

Big pretrained code encoders score ~95–98 macro-F1 on validation and then fall to 25–49 on test. This paper goes the other way: a handful of length-normalized ratios (how much of the snippet is comments, how verb-heavy those comments are, how much raw prose is mixed in), a depth-2 decision tree, and two rules found by reading the data. That reaches 67.35 macro-F1 on the official test set, trains on a CPU, and is readable end to end.

The problem with big encoders

Great on validation, lost on test

The authors first tried embeddings from three pretrained code models, each with the best downstream classifier. All three nearly solve the validation set and then collapse on the test set. Their explanation is language shift: 91.4% of training snippets are Python, so a model can learn Python-only cues such as indentation habits that mean little in C# or JavaScript.

Found by reading the data

The two rules

1 · The language name on its own line

Reading the training data by hand, the authors noticed LLM output often starts with a bare python or java line: leftover Markdown from a ```python fence with the backticks gone. About 5K of the 500K training samples have it. Flagging those gave +0.05 macro-F1 over an all-human baseline submission. How often each generator does this varies widely:

Leak rate = % of that model's snippets containing Markdown formatting (Table 3). Only the five models listed in the paper are shown.

2 · Too much prose → machine

The second rule uses the text-like ratio: the share of lines the code-vs-text classifier labels as natural language. Among samples with any prose, the average is 0.07 for human code and 0.17 for LLM code, and a Kolmogorov–Smirnov test says the distributions differ (D = 0.40, p < 0.001). The threshold is set well above both averages, at 0.3.

99.9%Human code left alone (specificity)
10.3%LLM samples flagged

Youden's J would put the cut at 0.008, which catches more LLM code and also flags human code. At 0.3 the rule catches only the most prose-heavy tenth of LLM samples, but almost never mislabels a human. Averages are over non-zero values on the training set.

Does it work?

Takeaway

Under distribution shift, pick signals that transfer

Large encoders learn whatever separates the classes in training, and here much of that was Python-specific. Comment density, verb-heavy explanations, stray prose and Markdown leftovers come from how LLMs write, not from which language they write in, so they survive the move to unseen languages and domains. The paper's appendix makes the same point from the model side: extra nonlinearity (random forest, MLP) hurt robustness, and a two-split tree did best.
